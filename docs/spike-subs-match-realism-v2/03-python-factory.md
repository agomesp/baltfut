# The Python offline "factory": static-safe ML for baltfut's subs game

## The pattern already exists here — name it and reuse it

The other AI describes the "factory" as if it's a new architecture to invent. It isn't: `experiments/ball-tracker/` already *is* the pattern, and its README states the invariant cleanly — **"its own venv + deps, nothing shared with the Next.js / Deno toolchain. The app never imports this; this never imports the app."** Heavy deps (torch, ultralytics, opencv) stay out of the bundle; the only integration point is a compact published artifact. That is exactly the train-offline / infer-in-browser split. So `experiments/football-models/` should be a sibling of `ball-tracker/`: own `pyproject.toml`, own `uv venv`, own pytest gate, zero coupling to the app's typecheck/lint/build gate.

The consumer side already exists too, and this is the single most important grounding fact the other AI missed: **`src/lib/ai-palpite/power.ts` is a hand-typed `POWER` table of ~60 team ratings, and `predict.ts` turns a rating gap into a scoreline with a linear formula** (`home = 1.3 + gap*0.6`, `gap = (hp-ap)/18`). This is *already* a thin TS evaluator reading baked coefficients — the coefficients are just hand-guessed instead of fitted. The factory's first deliverable is not a new system; it's **replacing 60 hand-typed integers and two magic constants with a fitted `public/models/team-strength.json`**, evaluated by the same-shaped `teamPower()`/`predictScore()` functions. That reframing collapses the "highest-ROI" proposal from "days of work, huge payoff" to genuinely small, because the seam is already cut.

## Pure-CPU vs GPU: the honest split

The other AI is correct that **predictions need no GPU** — and understates how correct it is. Dixon-Coles is a ~30-line MLE over a few hundred historical results; it fits in **CPU milliseconds**, not minutes. statsmodels or a hand-rolled `scipy.optimize.minimize` on the bivariate-Poisson log-likelihood both work. Monte-Carlo-ing the 32-team bracket 50k times is a tight integer loop, seconds on one core. **None of predictions, Elo/SPI, or bracket MC ever touches the 3060/5060.** The GPU only earns its keep on the RL/embedding path (proposal 3's PettingZoo+PPO, proposal 2's player-style embeddings) — and those are exactly the pieces V1 already flagged as weeks-plus stretch goals. So the GPU's role in *this* factory is near-zero for the high-ROI work, which is a point in favor of the whole approach: **the product's real feature ("IA vs você") is a laptop job.**

## The re-fit loop: GitHub Action, not "a tiny service"

The other AI hedges between "scheduled GitHub Action" and "a Supabase Edge Function writing to Storage." Kill the hedge. **Supabase Edge Functions are Deno — they cannot run Python, statsmodels, or numpy.** You could reimplement Dixon-Coles MLE in TS inside a Deno function, but that duplicates the model in a second language for no benefit. The clean answer, consistent with V1's "one Cloudflare Worker at most, no VPS" verdict, is:

- **Scheduled GitHub Action (Python, cron)** runs the factory, regenerates `public/models/*.json`, and commits it. The repo already has five workflows (`ci.yml`, `deploy-pages.yml`, `promos.yml`, etc.); adding `refit-models.yml` on a weekly cron is trivial and free. Push-to-main already auto-deploys Pages, so a committed JSON is live within a CI cycle. This is how it should work during a tournament: after each matchday, the Action re-fits attack/defense strengths and the site's predictions sharpen overnight — no server in the request path, ever.
- Writing to Supabase **Storage** instead of committing is only worth it if you need sub-CI-cycle freshness (intra-match Bayesian updates). For a once-a-day World Cup cadence, **committing to the repo is simpler, versioned for free, and diffable.** Reserve Storage for the case where an artifact must change without a deploy.

## Reproducibility, versioning, and the licensing trap

This is where the other AI is dangerously breezy, and where the project's own CLAUDE.md security-first posture demands discipline. Two hard rules:

1. **Do NOT vendor scraped FIFA/StatsBomb/FBref *data* into the public repo.** V1 already flagged this. StatsBomb Open Data is CC-BY-NC (non-commercial, attribution) and FBref/Opta terms forbid redistribution. The repo is public and even the *backups* are GPG-encrypted because they're public. The factory must keep **raw training data out of git** (gitignored, or fetched at Action runtime), and commit only **derived coefficients** — fitted numbers are not the copyrighted dataset. This is the single biggest legal trap and it's a one-line `.gitignore` mistake away.
2. **Reproducibility = pinned deps + a seed + a manifest.** V1's determinism keystone applies to the factory too. Every artifact JSON must carry a header: `{ "schema": 1, "generated_at": ..., "git_sha": ..., "data_through": "2026-06-29", "seed": 42, "model": "dixon-coles-v1" }`. The fit itself must be seeded (bracket MC uses a fixed RNG) so re-running the Action on the same data produces a **byte-identical** file — otherwise every cron run is a spurious diff and you can't tell a real model change from float jitter. Pin the Python deps in `pyproject.toml` with `uv lock`, exactly as ball-tracker isolates its stack.

## Bundle-size budget and ONNX reality

Static Pages over the `/baltfut` basePath means every artifact is a fetched static asset. Budgets:

- **Coefficient JSON (Dixon-Coles + Elo + a precomputed bracket-probability table):** trivial. ~60 teams × a few floats ≈ **2–10 KB gzipped.** A full 32-team pairwise scoreline probability *table* (32×32×~36 scoreline cells) is ~40k floats ≈ **100–300 KB** — fine as a lazy-loaded asset, and it means the browser does **zero** Poisson math, just a lookup. This precomputed-table route is the sleeper win the other AI underweights: it sidesteps V1's "Math.exp isn't bit-identical across engines" determinism trap entirely, because the browser never evaluates a PMF — it reads a number.
- **ONNX (RL policy net, style embeddings):** here the other AI is too optimistic. `onnxruntime-web` is **not free weight**: the WASM runtime is ~2–8 MB (SIMD/threaded builds larger), *plus* your model. A *tiny* MLP policy (a few dozen KB) is fine; anything CNN-ish balloons. On a free static host feeding a streamer's phone-heavy audience, shipping a multi-MB runtime for marginal realism is a bad trade. **Verdict: ONNX-in-browser is a real capability but a late-stage one; keep predictions as plain JSON + a 20-line TS Poisson/lookup evaluator and you never load onnxruntime at all.** If RL ever ships, prefer the V1-blessed pattern — GPU as an *offline producer* writing snapshots to Supabase Realtime — over shipping the net to every client.

## How this is actually shipped in the wild

FiveThirtyEight's SPI and club-soccer forecasts were **exactly this**: an offline model producing a static probability table, served as data, with the browser doing lookups — no live inference. Dixon-Coles (1997) is the canonical low-team-count football model and is genuinely ~30 lines. Football-data hobby sites routinely fit bivariate Poisson in a notebook and export JSON. The RL end (Google Research Football, PettingZoo) is real but is a research-grade, weeks-plus, GPU-bound effort that "looks weird before it looks brilliant" — correctly V1's stretch tier.

## Ranked pipeline (enabling-value vs effort)

1. **Dixon-Coles / bivariate-Poisson fit → `public/models/team-strength.json`, evaluated by the existing `ai-palpite` evaluator.** *Why:* it makes the headline "IA vs você" feature *earned* instead of 60 hand-typed guesses; predictions become defensible and update with results. *Effort:* **S–M** (the TS seam already exists; the fit is 30 lines). *Runs:* GPU-offline **not needed** — laptop/CPU; browser reads JSON. *Cost:* **$0.** *Libs:* statsmodels or scipy MLE; Poisson PMF in TS. *Tradeoff:* needs a legally-clean historical results source (results/scores are factual, not the copyrighted event data).
2. **Precomputed bracket-probability table (Monte-Carlo 32-team draw, seeded) → JSON.** *Why:* "BRA 55% / draw 24%" and per-team win% + expected round — the immersive prediction layer, and it dodges the browser float-determinism trap by baking the numbers. *Effort:* **S.** *Runs:* CPU-offline; browser lookup. *Cost:* **$0.** *Trap:* seed it or every cron run is a noisy diff.
3. **Weekly re-fit GitHub Action committing the JSON.** *Why:* predictions sharpen through the tournament with no server. *Effort:* **S** (copy an existing workflow). *Runs:* GitHub Action (Python). *Cost:* **$0** (free CI minutes). *Trap:* keep raw data gitignored; commit only coefficients + a reproducibility manifest.
4. **Data-calibrated sim constants + a real xG model → coefficient JSON consumed by `match-sim.ts` and `tournament.ts::simulateMatch`.** *Why:* unifies cosmetic play and the authoritative scoreline behind one calibrated model (V1's "one shared xG model" conclusion), replacing the current `poisson(0.35 + 2.4*ratio)` guesswork. *Effort:* **M.** *Runs:* offline fit (CPU; StatsBomb open data under NC terms, results only committed). *Cost:* **$0.** *Trap:* licensing — fit locally, ship coefficients not data.
5. **Multi-attribute player vectors from open per-90 metrics → player DB JSON.** *Why:* feeds the multi-attribute upgrade the sim wants; only worth it once real subs draft real players. *Effort:* **M–L.** *Runs:* offline CPU. *Cost:* **$0.** *Trap:* the current sim uses one scalar rating everywhere — this is not the "drop-in" the other AI claims; every `avgRating`/`SCORER_WEIGHT` call site assumes a scalar.
6. **RL policy / style embeddings → ONNX.** *Why:* true emergent behavior — but lowest product-ROI per V1. *Effort:* **L (weeks+).** *Runs:* **GPU-offline to train (3060 — 12GB, stable CUDA, prototype here); infer via GPU-producer→Supabase Realtime, NOT onnxruntime-web in every client.** *Cost:* $0 hosting, GPU electricity. *Trap:* onnxruntime-web runtime is multi-MB; reward-shaping is hard; defer.

## The one cheapest high-impact step, and the biggest trap

**Cheapest high-impact:** step 1 — fit Dixon-Coles and drop a `team-strength.json` into the *already-existing* `ai-palpite` evaluator. It's an S-effort swap of hand-typed numbers for fitted ones, needs no GPU and no server, and directly upgrades the product's marquee feature. **Biggest trap:** committing scraped StatsBomb/FBref/Opta *data* into the public repo (a CC-BY-NC / redistribution violation on a repo whose backups are already encrypted *because* it's public) — closely followed by shipping non-reproducible, unseeded artifacts that produce a noisy diff every cron run and hide real model changes.
