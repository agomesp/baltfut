# Home GPU as producer & optional live inference — honest verdict

## The load-bearing fact that reframes the whole question

V1's keystone was: make the sim **deterministic and seeded**, and broadcast only a seed. The code confirms this is achievable and cheap. In `tournament.ts::simulateMatch` the entire authoritative outcome is a handful of `Math.random()` calls — `poisson()` (line 99), scorer minutes `min()` (line 140), yellows/reds (lines 148–159), and the Fisher–Yates bracket shuffle (line 53). In `match-sim.ts` the cosmetic layer exposes a `Snapshot` of exactly 22 `{x:number,y:number}` positions plus the ball (lines 26–34). And `reactions.tsx` already runs a working Supabase Realtime broadcast (`.channel("reactions:"+matchId).send({...})`) carrying a *few-byte* payload with no DB write.

Put those together and the uncomfortable conclusion for the GPU-live pitch is: **once the sim is deterministic, a live GPU producer streaming positions is almost entirely redundant.** A ~30-byte seed + roster hash makes every browser recompute the identical match locally. Streaming 22 positions at 10–15 Hz *replaces* something you already get for free. So the GPU's live role has to justify itself against a $0 client-side baseline — and mostly it can't. That is the central critique of the second AI's "PRODUCER → Supabase Realtime" pattern: it's technically fine and cheap, but it's solving a problem the determinism keystone already dissolved.

## The three patterns, graded honestly

**(i) OFFLINE FACTORY — the safe default, and the *only* pattern I fully endorse.** GPU is powered on only when the owner runs a job; users never touch it. It trains/crunches, exports a compact artifact (JSON coefficients, a probability table, or an ONNX net ≤ a few MB), and that artifact is committed to the static bundle or pushed to Supabase Storage. This is exactly how the existing `ai-palpite/` modules already work in spirit — `simulate.ts` is a pure, deterministic, CPU-only projection with *no* GPU anywhere. The factory pattern is correct because it inherits none of a home box's liabilities: no uptime SLA, no NAT/uplink exposure, no request-path coupling. The second AI is right here.

**(ii) PRODUCER → Supabase Realtime.** Bandwidth is genuinely trivial — 22 players × (2 × int16) + ball ≈ 96 bytes/frame; at 15 Hz that's ~1.4 KB/s per *source* (not per client — Realtime fans out server-side). The second AI's "streaming 22 positions is tiny" claim is **true on bandwidth but wrong on quota framing.** Supabase's free tier meters *messages*, and the meter is 2M messages/month. At 15 msg/s a single continuously-running match burns ~1.3M messages **per day** — you blow the entire free monthly quota in ~36 hours of one stream. You'd have to batch (send 0.5 s bundles, drop to ~2 msg/s and interpolate client-side) to survive, which is real engineering, not a freebie. And even then you've spent effort to *reintroduce non-determinism risk* (`Math.hypot`/`Math.exp` at lines 72/118 in match-sim, line 100 in tournament — the exact cross-engine float trap V1 flagged) that the seed-broadcast avoided by never trusting client floats. **Verdict: over-scoped. Only justified if the sim is *not* client-runnable** — e.g. a neural-policy sim too heavy for `onnxruntime-web` on a weak phone. That's a narrow, hypothetical future, not now.

**(iii) FastAPI behind Cloudflare Tunnel / Tailscale Funnel.** This is the "put the residential box in the request path" pattern, and it's justified in exactly one scope: **personal / streamer-only tooling.** A Cloudflare Tunnel (free) means no inbound port-forward, no exposed residential IP, origin authenticated by Cloudflare — security is defensible *if* you gate it (Cloudflare Access, or a bearer token the Edge Function holds). But it is a hard single point of failure: home power blip, ISP CGNAT reset, Windows update reboot, or the owner closing the laptop, and every viewer sees a dead feature mid-stream. For a public audience that's unacceptable; for the streamer's own control panel (kick off a match, re-run a Monte-Carlo) it's fine because the streamer is present anyway. **Verdict: keep it behind the streamer's own hand, never in a viewer's render path.**

## What actually needs a GPU

Almost nothing this product needs. Predictions — Dixon-Coles MLE, Elo/SPI updates, a 10–50k-run bracket Monte-Carlo — are **CPU-millisecond** work. Fitting ~50 team attack/defense coefficients is a few-line `scipy.optimize` call; a 32-team Monte-Carlo bracket is a tight loop that finishes in under a second on a laptop core. The second AI concedes this ("predictions need NO GPU") and is correct — so patterns (ii)/(iii) buy the prediction product *nothing*. The GPU only earns its keep on the RL self-play path (PettingZoo/Gymnasium + PPO, Google-Research-Football-style) and on player-style embeddings from event data — both of which V1 and the effort math put at weeks+, both of which export an ONNX net that then runs *client-side* via `onnxruntime-web`. In other words: even the RL path uses the GPU as **factory, not server.** There is no live-GPU requirement anywhere in the realistic roadmap.

## Hardware call: 3060 12GB vs 5060 8GB

For *training* — which is the GPU's only real job here — the **RTX 3060 12GB wins decisively**, and it's not close. VRAM is the binding constraint for RL self-play (replay buffers, parallel envs, larger policy/critic nets) and for any embedding model; 12GB rock-solid Ampere with mature CUDA 12.x + stable PyTorch wheels beats 8GB Blackwell that needs CUDA 12.8+ and bleeding-edge toolchain fiddling. RL reward-shaping already "looks weird before brilliant" (V1); you do not want to also be debugging Blackwell wheel breakage. The 5060's edge is *inference* throughput and efficiency — irrelevant, because inference here is either CPU (predictions) or client-side ONNX (RL policy). The second AI's "prototype/train on the 3060, serve/infer on whichever" is right, with the sharpening that **you never serve from either** in the default architecture. Train on the 3060; ship the artifact.

## Cheapest high-impact first step, and the biggest trap

**Cheapest high-impact:** the offline **Dixon-Coles + Monte-Carlo factory** — *no GPU, no home box, no server*. Fit on a GitHub Action (Python), export a ~50-team coefficient JSON + a per-team bracket-win-probability table to Supabase Storage, and have TS evaluate a Poisson PMF for "BRA 55% / draw 24% / ARG 21%." This is the "IA vs você" product, it costs $0, and it fits the existing `ai-palpite/` seam exactly.

**Biggest trap:** standing up the home GPU as a *live producer* (pattern ii/iii for the public pitch). It reintroduces the float-determinism hazard the seed-broadcast eliminated, quietly detonates the Supabase message quota, and welds a residential box's uptime to your uptime — all to replace positions every client can already recompute for free.

## Ranked recommendations

1. **Offline Dixon-Coles + Elo/SPI + bracket Monte-Carlo → JSON.** *Why:* delivers the real "IA vs você" product; predictions and play finally agree. *Effort:* M. *Runs:* GitHub Action (Python) → Supabase Storage; TS reads JSON. *Cost:* $0. *Libs:* `scipy.optimize`, plain NumPy Monte-Carlo. *Tradeoff:* needs a clean (non-scraped, licensing-safe) results feed.
2. **GPU = OFFLINE FACTORY only, for the RL/embedding path.** *Why:* the sole place a GPU adds realism (emergent play); ships as client ONNX. *Effort:* L. *Runs:* GPU offline (3060) → ONNX in `onnxruntime-web`. *Cost:* electricity only. *Libs:* PettingZoo/Gymnasium + PPO, ONNX export. *Tradeoff:* reward-shaping is slow; do utility-AI in TS first.
3. **Streamer-only FastAPI behind a Cloudflare Tunnel.** *Why:* lets the streamer trigger re-fits / kickoffs on demand without exposing the box. *Effort:* S–M. *Runs:* home GPU/CPU + Cloudflare Tunnel (free), token-gated. *Cost:* $0. *Tradeoff:* single point of failure — acceptable only because the streamer is present.
4. **Live GPU producer → Supabase Realtime.** *Why (thin):* only if a future neural sim can't run client-side. *Effort:* M + ongoing ops. *Runs:* home box (must be up). *Cost:* risks paid Supabase tier on message quota. *Tradeoff:* redundant against the deterministic seed-broadcast; batch/interpolate or die. **Deprioritize.**

**Bottom line:** for this product the GPU should be a *factory that is off when users visit*, exporting artifacts a static client consumes. Nothing about the deterministic-sim architecture wants a live residential box in the loop. Stay client-deterministic; let the GPU train, not serve.
