# Architecture, Hosting, Realtime, Determinism & GPU — the definitive 3-bucket plan

## 1. Critique of the v1 + v2 material for this theme

I re-read the four theme docs plus both ROADMAPs and the v2 ARCHITECTURE, and verified the load-bearing code facts: `match-sim.ts` has **20** `Math.random()` calls, `tournament.ts` has **11** (31 total, not v1's "~20 in match-sim"); the Realtime broadcast seam already ships (`src/components/reactions.tsx:60` `.channel("reactions:"+matchId)`, plus `page.tsx:344/363/389` palpite/pen/window channels). So the plumbing this theme depends on already exists in production form.

**What holds up (both spikes agree, and they're right):**

- **The determinism keystone is correct and non-negotiable.** Making the sim a pure function of `(seed, tick)` and driving it off a *server-owned start timestamp* rather than accumulated `rAF` dt is the single hinge that keeps everything free. It simultaneously delivers watched-together (same seed → identical frames, the classic RTS/GGPO lockstep property), self-heals the background-tab freeze (a re-focused tab recomputes `elapsed` and fast-forwards), and gives free deterministic replays from a `(seed, lineups)` tuple. Both docs land this; it is the correct #1.
- **"You do not need a server for compute" is correct.** 22 tokens × a few `Math.hypot`/`lerp` per frame is sub-millisecond. The expensive-sounding parts (heavy sim, authoritative live loop, scheduled kickoff) collapse to *cheap* parts once the sim is deterministic: compute is client-side, "authority" is a tiny DB row + broadcast, scheduling is `pg_cron`.
- **The GPU verdict is correct and refreshingly honest.** For this product the GPU is a *factory that is off when users visit*. Predictions (Dixon-Coles MLE, Elo, 50k-run bracket Monte-Carlo) are CPU-millisecond work — they never touch a GPU. The quota math is the killer argument the v2 GPU doc nails: a live position-producer at 15 msg/s exhausts Supabase's 2M-msg/month free quota in **~36 hours**, and it's *redundant anyway* because a 30-byte seed recomputes the match on every client for free. **Verdict holds: the GPU trains artifacts, it never serves.**
- **Python-factory-as-GitHub-Action, not Edge Function.** Supabase Edge Functions are Deno — they cannot run scipy/statsmodels. Both v2 docs correctly kill the "or an Edge Function" hedge. A weekly cron Action that regenerates `public/models/*.json` and commits it is the only sane re-fit loop, and push-to-main already auto-deploys Pages.

**Where v1 is over-optimistic / wrong (v2 catches most of it; I confirmed against code):**

- **v1's determinism refactor points at the wrong file.** v1 says "replace ~20 `Math.random()` in `match-sim.ts`." But the *authoritative* scoreline, scorers, minutes, cards, **and the entire bracket draw** are all `Math.random()` in `tournament.ts` (Fisher–Yates `shuffle` line 53, `poisson`, scorer `min()`, cards, shootout). Seed only `match-sim.ts` and every viewer sees synced cosmetic dots over a *different scoreline and a different bracket*. v2's correction is right: **seed `tournament.ts` FIRST.** The broadcast payload is therefore `{bracketSeed}` + per-match seeds — not `{seed, startEpochMs, goalScript}`.
- **`{seed}` and `{goalScript}` broadcasts are alternatives, not complementary** — v1 lists them together. If goals are derived from the seed via `tournament.ts`, there is no separate goalScript to send. Pick seed-only (canonical, ~30 bytes, requires seeding the outcome RNG). This is the cleaner choice and I endorse it.
- **Float determinism is NOT free "because it's one JS engine."** `Math.hypot`/`Math.exp`/trig are not IEEE-754 bit-identical across V8/JavaScriptCore/Gecko (last-ULP transcendental differences); over 5400 fixed steps the *cosmetic* dots micro-diverge across browsers. This is fine for cosmetics and fatal if you ever derive authority from float positions. The hard rule both docs should state louder: **keep authority in `tournament.ts` integers; never trust a float position across clients.**
- **v1 under-scopes `pg_cron` scheduled kickoff as "S."** It needs `pg_net` + a vaulted service key, idempotency (cron can double-fire), Edge cold-start, and — per the project's own "Grants gotcha" — every new table (`matches`, `subs_*`) needs explicit grants to *both* `service_role` and `anon` plus RLS plus `scripts/db/` assertions or CI's `database` job goes red. Call it **M**, and budget the recurring grants tax on every Supabase item.
- **Presence is chatty.** v1 sells "142 subs watching" via Presence as near-free; every join/leave/heartbeat counts against the 2M-msg quota, and the free project **pauses after 7 days idle** — a live footgun for an appointment-event product that v1 buries in the escalation table rather than flagging as a launch risk.

**What's genuinely MISSING from both:** neither doc gives a concrete **clock-sync protocol** (both hand-wave "Cristian's algorithm / NTP-lite"); neither specifies a **catch-up cap** as a hard number to avoid the spiral-of-death after a long-hidden tab; and neither addresses **schema/replay versioning** — a deployed sim-logic change silently breaks determinism for in-flight replays unless the `(seed)` tuple carries an `engineVersion` and old replays pin the old engine.

## 2 & 3. The definitive long-game plan, every step BUCKET-tagged

### BUCKET A — $0 / current stack (GitHub Pages + Supabase free + free Actions)

This bucket carries the entire critical path. Nothing here needs money.

- **A1 — Seed the RNG in `tournament.ts` FIRST, then `match-sim.ts` (one `mulberry32` stream, ~31 sites). [BUCKET A]** *Why A:* pure client TS, zero infra. It is the keystone — outcome-sync, replays, and watched-together all derive from it. Do it TDD-first (same seed → identical `MatchResult[]`, then identical snapshots after N ticks). Rank **1**.
- **A2 — Fixed 1/30s timestep + accumulator, decoupling sim tick from render Hz; derive match minute from `Date.now()`. [BUCKET A]** *Why A:* client-only; fixes the frame-rate-dependent `dt` divergence and kills the *solo* tab-freeze immediately (the precompute+`clock` reveal model in `tournament-view.tsx` makes this nearly free). Rank **2**, do it *with* A1.
- **A3 — Web Worker sim on `setInterval(1000/30)`, main thread interpolates last two snapshots only when visible. [BUCKET A]** *Why A:* Workers are throttled less than `rAF` in a *backgrounded* (not occluded) tab. **Honesty rule:** this does NOT survive full OBS occlusion (the project's own memory proves timers/workers/WSS/audio all freeze) — never sell the crowd-bed or worker as an occlusion fix. Rank 6.
- **A4 — Watched-together: broadcast `{bracketSeed, perMatchSeeds, startEpochMs}` over the existing Supabase Realtime channel; clients recompute + fast-forward to `targetTick`. [BUCKET A]** *Why A:* Realtime free tier (200 concurrent, 2M msg/mo) comfortably fits *seed + events*, not positions. Zero per-tick messages. Reuses the shipped `reactions.tsx`/`page.tsx` broadcast pattern. Rank **3**.
  - **Clock sync (the missing spec):** on join, ping a tiny Edge `now()` 3× and take the **median** round-trip offset (Cristian's algorithm); sub-100ms is plenty for cosmetics.
  - **Catch-up cap (the missing spec):** if a resumed tab is >3s behind, fast-forward the *simulation* but **skip rendering intermediate frames**; hard-cap the loop so it can never spiral.
- **A5 — Join-in-progress via one durable `match_state` row `{match_id, bracket_seed, start_epoch, status}`. [BUCKET A]** *Why A:* anon SELECT under existing RLS; because the sim is deterministic + clock-driven, **no per-tick state is stored** — the row + elapsed reconstructs the exact frame. Rank 4.
- **A6 — Presence spectator count + synchronized-kickoff lobby (countdown to `kickoff_at`). [BUCKET A]** *Why A:* built into the Realtime channel. **Caveat:** Presence churn burns the message quota — this is a real (if soft) ceiling that eventually pushes to Bucket B. Rank 5.
- **A7 — Persisted replays from the `(seed, lineups, engineVersion)` tuple. [BUCKET A]** *Why A:* bytes per match in Postgres/Storage; `engineVersion` pins old replays to old sim logic (the versioning gap both docs missed). Rank 8.
- **A8 — Scheduled kickoff + bracket advance via `pg_cron` + Edge Function. [BUCKET A, but honestly M]** *Why A:* `pg_cron` + stateless function is the free-tier sweet spot; makes the tournament a real event even if no client is open. **Tax:** `pg_net` + vaulted key + idempotency + new-table grants/RLS/`scripts/db/` assertions. Rank 7.
- **A9 — Python offline factory `experiments/football-models/` (sibling of `ball-tracker/`) → Dixon-Coles / bracket-MC / xG coefficient JSONs, re-fit by a **weekly GitHub Action** committing `public/models/*.json`. [BUCKET A]** *Why A:* CPU-only (no GPU), free CI, browser reads JSON via the existing `ai-palpite` `predict.ts`/`power.ts` seam. **Hard rules:** raw StatsBomb/FBref data stays gitignored (CC-BY-NC on a public repo); commit only derived coefficients + synthetic samples; every artifact carries a seeded reproducibility manifest so cron runs are byte-identical. Rank 4-tier (feature-critical but parallel to the sim work).

**A-bucket determinism guardrail (state it as a code-review gate):** two planes. **Authority plane** (`tournament.ts` + sim authoritative positions, utility-AI *selection*) → seeded PRNG, scaled-integer utilities, a 256-entry integer-exp LUT for softmax, fixed-point CDF over `λ·1000` — **never `Math.exp` in authority** (which `poisson()` currently violates). **Cosmetic plane** (lean/bob, sprites, IK limbs) → floats fine, read-only, **must never write back**. This single rule is why Rain-World-style animation is safe.

### BUCKET B — + one cheap server: what it actually buys, and the cheapest right option per need

Bucket A cannot do three things: (a) hold a **persistent secret + token-refresh loop**, (b) survive the **7-day free-tier pause** for an appointment product, (c) exceed **200 concurrent Realtime connections** or run a **server-authoritative live loop with live user inputs**. Each has a *different* cheapest answer — do not buy one box for all three.

- **B1 — Twitch OAuth sub-gating + EventSub / Predictions bot. [BUCKET B]** *Why B, not A:* a static bundle **cannot** hold the broadcaster token or refresh it hourly, and EventSub needs a persistent WebSocket. This is the first thing that genuinely breaks the "$0" story. **Cheapest right option: one Cloudflare Worker (free up to ~100k req/day → $5 Workers Paid) + Durable Object** for the EventSub socket and token cache. Not a VPS. Gate *owning a team*, not spectating.
- **B2 — Kill the 7-day pause / raise Realtime to 500 conns / more egress. [BUCKET B]** *Why B:* only tier that removes the pause in one move. **Cheapest right option: Supabase Pro $25/mo**, zero ops. Buy it only when a real stream makes the streamer's browser load-bearing or Presence churn threatens the 2M-msg quota — i.e. when A6's soft ceiling becomes a hard one.
- **B3 — Server-authoritative live loop with live mid-match user inputs / >200 spectators. [BUCKET B]** *Why B:* the *only* scenario the deterministic client model can't cover (it kills clock-drift, cheating, and join-in-progress for real-money-style integrity). **Cheapest right option: Cloudflare Durable Objects + WebSocket Hibernation** — free up to ~3M req/mo, **bills nothing while idle**, gives a genuine authoritative room. Reach for **Fly.io (~$2/mo shared-cpu-1x) or Hetzner (€4)** *only* if you need a persistent stateful Node game server (Colyseus/Hathora) — given the cosmetic-sim design, that day may never come.
- **B-trap:** **never** host the kickoff path behind a cold start. Render's free spin-down (~60s) is disqualifying for a "live match starting now" product. DO hibernation and Fly always-on avoid it; Render/Railway scale-to-zero do not.

**What MOVES to B vs stays in A:** scheduled kickoff **stays in A** (`pg_cron` handles it free; a server buys nothing here). Twitch bot and the authoritative live loop are **born in B** (A physically can't). The pause-removal is a B *convenience* that A can defer with a keep-alive ping until scale forces it.

### BUCKET C — + GPU, in two modes

- **C1 — GPU as OFFLINE FACTORY feeding artifacts (the only mode I fully endorse). [BUCKET C]** *Why it needs C:* the *sole* place a GPU earns its keep is training an **RL self-play policy / player-style embeddings** → exported ONNX (tens of KB), committed and re-fit via the A9 Action pipeline. Predictions never come here (CPU-ms). **Hardware: RTX 3060 12GB decisively** — VRAM is the RL binding constraint (replay buffers, parallel envs), and mature CUDA 12.x + stable PyTorch wheels beat the 5060's 8GB Blackwell + bleeding-edge toolchain. You train on it; you never serve from it. **Honest tradeoff:** RL *fights the authoritative scoreline* — a smart agent that loses because the dice said so looks broken, worse than the current FSM. Scope it to **off-ball motion only** and keep it a research spike, not a roadmap item. This is what C unlocks that B cannot: learned emergent behavior — but the ROI is genuinely low here, so C1 is "possible, deprioritized."
- **C2 — Streamer GPU running heavy things LIVE IN-BROWSER (WebGPU / onnxruntime-web). [BUCKET C]** *Why it needs C:* only worth it if a neural sim is too heavy for a weak phone, or for high-fidelity WebGPU procedural rendering / large sims on the streamer's own strong machine. **Honest fragility:** onnxruntime-web ships a **2–8 MB WASM runtime** to a phone-heavy audience for marginal realism; worse, **float matmuls break cross-client seed-replay** (WASM vs WebGPU produce different bits) — it *detonates the determinism keystone* unless int8-quantized + backend-pinned. **Verdict: avoid for shared/authoritative content; acceptable only for the streamer's own local high-fidelity view.**
- **C3 — Home GPU as a LIVE PRODUCER → Supabase Realtime (streaming positions). [BUCKET C, reject].** *Why reject:* it's redundant against the $0 seed-broadcast (every client already recomputes the match), it detonates the 2M-msg quota (~36h of one stream), and it re-introduces the float-drift the seed avoided. If ever used for a truly-uninferable neural sim, it must batch to ~2 msg/s + client-interpolate — real engineering for a capability the deterministic baseline gives free.
- **C4 — Streamer-only FastAPI behind a free Cloudflare Tunnel (token-gated) for the owner's control panel. [BUCKET C-adjacent].** *Why acceptable:* a residential box in the request path is a hard single point of failure (power blip, CGNAT reset, closed laptop) — acceptable **only** because the streamer is present anyway. Never a viewer feature; never in a viewer's render path.

**Honest C tradeoffs overall:** uptime (residential box has no SLA), NAT/security (Tunnel mitigates exposure but is still SPOF), quota (live producer blows Supabase's message meter), and — the deepest one — **determinism-break**: any float ML shipped to clients or streamed across them shatters the seed-replay invariant that makes the whole free architecture work. The GPU's honest place is: **train an artifact you probably won't build; never serve.**

## Target architecture per bucket (one-liners)

- **Bucket A:** deterministic seeded sim in a Web Worker, stepped fixed-timestep against a broadcast `startEpochMs`, painted only when visible; Supabase `match_state` row + seed/event Realtime broadcast + Presence; `pg_cron` kickoff; Python-factory JSON re-fit by GitHub Action; replays from `(seed, lineups, engineVersion)`.
- **Bucket B:** all of A, plus **one Cloudflare Worker + Durable Object** (Twitch OAuth/EventSub, token cache, and — if ever needed — an authoritative hibernating live room for >200 viewers), and **Supabase Pro $25** *only* to kill the pause / raise conn+quota at real scale.
- **Bucket C:** all of B, plus the **RTX 3060 as an offline factory** exporting ONNX to the same artifact pipeline (RL off-ball motion, deferred); optional streamer-local WebGPU high-fidelity view; a token-gated Cloudflare-Tunnel FastAPI control panel for the streamer's own hand. **No live GPU in any viewer's path, ever.**

**Do A1 (seed `tournament.ts` first) before anything else — it is the hinge that keeps every other item in Bucket A free.**
