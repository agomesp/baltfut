# Visuals, Audio & Broadcast Immersion — the V3 verdict

## 1. What holds up, what's mis-scoped, what's missing (critique of v1 + v2)

I read both pitch renderers and all four docs. The single most important fact — one v1's `03-rendering-visuals.md` gets **wrong** and v2's `07-retro-visuals.md` / `01-procedural-animation.md` get **right** — is the state of the code. v1 line 3 asserts the "pseudo-3D CSS pitch" exists and that its #1 job is to "stop routing per-frame motion through React," describing `~11 setState calls per frame` in `subs-draft/pitch-view.tsx`. That file *does* exist and *does* do exactly that (lines 99–118: `setHomePos`, `setAwayPos`, `setBall`, `setBallTrail`… every rAF). **But v2 already built the Canvas2D successor** at `subs-draft2/pitch-view.tsx` — a single `<canvas>`, one `draw()` per frame, event-driven `setState` only for overlays (lines 132–147), depth-sorted painter's order (line 331), foot-planting IK legs with analytic 2-bone solve (`ikLeg`, lines 372–382), velocity/accel-driven lean and gait (`stepGait`, lines 255–300). So v1's "QUICK WIN #1: move the loop off React state → Canvas2D" **is already done in v2**. The two spikes are talking past each other: v1 ranks the Canvas migration as the top unstarted item; v2's `01-procedural-animation.md` line 5 correctly warns that migration is "the weeks-scale item" — and then v2 *shipped a prototype of it*. **The V3 reconciliation: the substrate question is settled. `subs-draft2` is the render baseline. v1's #1 is retired; everything else in v1 re-ranks against the Canvas baseline, not the CSS-3D one.**

What **holds up** across both:
- **The cosmetic/authority firewall.** v2 `01-procedural-animation.md` §"determinism landmine" is the sharpest single insight in the whole set: the IK/Verlet body layer uses `Math.sin/sqrt/lerp`, is non-reproducible across engines, and is therefore *safe only because it's read-only decoration* over integer-authoritative positions from `tournament.ts`. The `subs-draft2` code honors this — velocity is derived by finite difference locally (lines 157–158), never fed back. This must remain law. **[A]**
- **Sprites-per-effort is the right default** (v2 `07-retro-visuals.md` §a). 8-dir billboards from the owner's PixelLab pipeline map 1:1 to the deliverable; the math (`atan2(vy,vx)` bucketed to 45°, frame `= floor(dist/stride)%n`) is trivial and integer-safe.
- **Three.js is over-scoped** (both docs agree): rigged glTF + instancing + `EffectComposer` is weeks of content work for a look sprites deliver at ~5% cost.
- **Audio's "finite templates → build-time TTS" insight** (v1 `08-commentary-audio.md` #5B) is genuinely clever: because the phrase bank is a *finite fragment set*, you pre-generate every fragment once with cloud TTS and stitch at runtime like EA FC — broadcast voice at zero runtime cost. And the **"never an LLM/TTS on the live per-event path"** trap (kills static hosting + offline + latency at once) is correct and non-negotiable.

What is **over-optimistic / under-scoped**:
- **Foot-lock tuning.** v1 hand-waves gait; v2 `01` correctly flags it as ~a week of tuning *alone* to avoid ice-skating/moon-walking. The shipped `stepGait` (subtests2 lines 255–300) is a *charming first pass*, not convincing — stride/trigger thresholds are un-tuned magic numbers (`0.16`, `0.85`, `stance=1.5`) and there's no ragdoll on `foul()`. Honest cost to *convincing*: 3–5 weeks, per v2 — that estimate holds.
- **v1's audio "#7 rAF-freeze fix" undersells the ceiling.** Project MEMORY (`background-tab-throttling`) proved audio+worker+WSS+video **all froze under full OBS occlusion** — not web-fixable. v1 `08` #7 line 28 does admit this but #4 (crowd bed "keeps playing while hidden") over-promises: it survives *backgrounded-but-visible* tabs, not occlusion. **This is the single most load-bearing correction for a streamer product: audio does NOT reliably survive the exact condition (OBS-covered browser source) the streamer runs in.** The mitigation is operational (keep the source visible / OBS-specific flags), not code.

What's **missing** from both:
- **No camera/replay system was actually built.** v1 #3 (pan/zoom-to-ball, cut-on-goal, slow-mo replay from a snapshot ring-buffer) is the biggest *"we're watching a broadcast"* lever and it's absent from both prototypes — `subs-draft2` has a fixed projection (`proj`, lines 52–59), no `ctx.setTransform` camera. This is the highest-value unbuilt visual work.
- **No pixel-skin-over-IK reconciliation is coded.** Both docs *name* the Rain-World "cosmetic mesh over physics" trick (draw PixelLab limb sprites along the Verlet bones) but neither resolves how the sprite path and the IK path *co-exist*. They're presented as alternatives; they should be **layers**.
- **No dynamic-range/ducking audio mix, no master-mute for streamers** beyond a one-line mention. For a product a streamer overlays their mic on, the mix bus is a feature, not a footnote.

## 2. The definitive long-game (no time constraints)

Rendering is a **layered stack, not a fork**. Reconcile the IK-body path and the sprite/3D paths by making them successive skins over one motion source:

1. **Motion source (settled):** integer positions from `tournament.ts`/`match-sim.ts` → local velocity/accel by finite difference. First, **widen `snapshot()` to emit `{x,y,vx,vy,role,id}` + a `phase` flag** (`dribble|pass|shot|loose`) so skins stop re-deriving semantics (v2 `07` #1 / v1 `08` #1 agree). **[A]**
2. **Skin layer 0 — capsule IK skeletons** (`subtests2` today): the substrate baseline. **[A]**
3. **Skin layer 1 — pixel-art limb segments** drawn *along* the same IK bones (PixelLab-generated torso/thigh/shin/arm strips, recolor-tinted per kit). This is the Rain-World mesh-over-physics answer AND the retro-sprite answer *unified*: the physics is the IK skeleton; the pixels are a skin over it. Fixed 8-dir billboards become the **fallback/LOD** for far/off-ball players; ball-carrier + nearby players get full IK-skinned limbs. This is how the two "competing" paths reconcile — they are LOD tiers of one pipeline. **[A]** (art gen: PixelLab credits, effectively $0).
4. **Camera + replay** (the missing broadcast lever): a `ctx.setTransform(scale,…,-camX,-camY)` layer over the canvas; `camX/camY` critically-damped-eased toward the ball with velocity lookahead and a dead-zone box (no 1:1 chase → nausea). A 3–4s ring-buffer of snapshots enables **cut-to-slow-mo replay on goal** at 0.35× with a "REPLAY" bug — pure re-render of stored frames, no video. **[A]**
5. **Broadcast overlays** — corner radar/minimap, lower-third name bugs on the carrier and on goals, possession arrow, LIVE/REPLAY bugs, ducked stat-pop on goals. Pure DOM/React over the canvas, zero per-frame cost. **[A]**
6. **Audio stack** — Web Audio (not `new Audio()`) single `AudioContext`, gated behind the existing play button (autoplay policy). SFX one-shots (whistle/kick/net/post/tackle/roar, ~300KB from freesound CC0/Kenney) on `phase`/`eventSeq`; an **adaptive crowd bed** whose gain + low-pass track a smoothed `danger` (derivable from distance-to-goal + defenders, per v1 `08` #1); a **mix bus with ducking** (crowd ducks under commentary) and a **master-mute + volume** for streamers. **[A]**
7. **Commentary** — pt-BR templated phrase bank keyed by `kind × danger-bucket × context`, ≥6 variants/slot with recent-history dedupe, split play-by-play vs colour/idle-filler. Web Speech `speechSynthesis` as the free voice tier; **build-time cloud TTS of the finite fragment set → Supabase Storage** as the broadcast tier. **[A for text + Web Speech; B for the cloud-TTS build step]**
8. **Sync ("watched together")** — broadcast the authoritative clock + discrete goal timestamps over Supabase Realtime (NOT positions), each client's deterministic sim fills between, so the stadium roar lands within ~1s for everyone. **[A]**

Where the **GPU meaningfully raises fidelity (C)** — and where it does *not*:
- It does **NOT** help the 22-player IK layer (≈180 points; v2 `01`/`07` both: "GPU earns nothing here"). Capsules or pixel-skinned limbs for 22 bodies are Canvas2D-trivial. **[A, correctly]**
- It **does** raise fidelity when you deliberately blow past the Canvas2D budget: (i) **WebGL/WebGPU (Pixi v8 or a hand-rolled pipeline)** for hundreds of animated sprites + particle celebrations + cheap post-FX (motion blur, bloom, CRT/palette-quantize shader) — the *retro-3D pixelation* look v2 `07`(b) wanted, but achieved as a full-screen shader over the 2.5D scene rather than rigged 3D; (ii) **onnxruntime-web / WebGPU** for the streamer's browser to run a heavier *cosmetic* animation model live (e.g. a learned gait/pose net, or neural upscaling of low-res sprites) — strictly cosmetic, determinism-safe; (iii) the **home GPU as an offline factory** producing higher-fidelity assets (PixelLab-style sprite sheets at scale, baked lighting, pre-rendered voxel-to-sprite turntables) committed as static PNGs — no runtime GPU needed. The honest tradeoff: (i)/(ii) need a WebGPU-capable client (the *streamer's* machine, fine; a phone viewer, not), grow the bundle, and must stay off the authority path; (iii) is pure win but is a build-time convenience, not a runtime capability.

## 3. Every step, bucket-tagged and ranked (within this theme)

**BUCKET A — $0, current stack (GitHub Pages static + Supabase free + free Actions).** Realism lives on the client; none of this needs a server.

1. **Widen `snapshot()` to `{x,y,vx,vy,role,id}` + `phase`.** **[A]** — cheapest high-impact step; unblocks every skin/audio layer identically; additive, tests stay green. *Ranked #1.*
2. **Adopt `subtests2` Canvas2D as the render baseline; retire the `subtests` CSS-3D/React-state loop.** **[A]** — the substrate is *already built*; this is a decision + cleanup, not the "weeks" migration v1 feared. *#2.*
3. **Camera + goal replay (setTransform + snapshot ring-buffer).** **[A]** — the single biggest broadcast-feel gain and it's currently unbuilt; pure client math. *#3.*
4. **Audio stack: Web Audio SFX + adaptive crowd + mix bus/ducking + master-mute.** **[A]** — highest immersion-per-KB; assets on Supabase Storage (still free tier). *#4.*
5. **Templated pt-BR commentary + Web Speech voice tier.** **[A]** — variety+reactivity is 80% of "alive"; free/offline/localized. *#5.*
6. **Broadcast overlays (radar, lower-thirds, LIVE/REPLAY bugs, stat-pops).** **[A]** — cheap DOM-over-canvas polish. *#6.*
7. **Foot-lock/gait tuning to "convincing" + ragdoll on `foul()`.** **[A]** — the 3–5-week craft item v2 correctly sized; pure TS. *#7.*
8. **Pixel-skinned IK limbs via PixelLab (LOD: 8-dir billboard far, skinned-IK near).** **[A]** — reconciles the sprite and IK paths as LOD tiers; PixelLab credits ≈ $0; static PNGs in `public/`. *#8.*
9. **Supabase Realtime clock/event sync for communal roar.** **[A]** — free-tier Realtime; sync clock+events only, never positions. *#9.*

*Why these stay in A:* every item is client-side cosmetic decoration over integer authority, or free-tier Storage/Realtime for assets/sync. No continuous compute, no server loop, no money.

**BUCKET B — + one cheap paid host (Cloudflare Workers+DO free–$5 / Fly.io–Hetzner ~$2–5 / Supabase Pro $25).** What B *unlocks for this theme*, and what moves here:

- **Build-time cloud TTS pipeline (ElevenLabs/Azure Neural pt-BR) → Storage.** **[B]** — the finite-fragment set is voiced *once* by a GitHub Action (Actions is free, but the TTS API costs a few dollars of credits → the "+cheap paid" line). Gives broadcast-grade voice with zero runtime cost. This is the *only* audio item that needs paid resources, and only at build time. *Top of B for this theme.*
- **Scheduled/server-authoritative kickoff + timekeeper** for synced watch-alongs at a fixed time (a Worker/cron holds the master clock instead of a client host). **[B]** — moves the sync *timekeeper* (not the render) to B; the roar-sync itself (A#9) still works client-hosted, B just makes it reliable/scheduled and removes the 7-day Supabase pause risk.
- **Twitch EventSub/chat bot** driving overlays (sub-goal shout-outs, chat-voted MOTM lower-thirds). **[B]** — needs a persistent listener a static site can't host.

*What stays in A:* all rendering, SFX, crowd, text commentary, Web Speech, camera, replay, overlays. B buys *voice quality*, *scheduling*, and *chat integration* — not fidelity of the pitch itself.

**BUCKET C — + GPU.** What C unlocks that B cannot:

- **(i) Home GPU as offline asset factory** → higher-fidelity committed static assets: large recolorable sprite atlases, voxel-turntable-to-sprite bakes, baked pitch/stadium lighting, pre-rendered celebration cinematics. **[C, mode-i]** — commits PNGs/JSON; *runtime stays A*. Pure fidelity win, no uptime/quota risk.
- **(ii) Streamer-browser WebGPU/onnxruntime-web** for a full-screen post-FX pipeline (bloom, motion blur, CRT/palette-quantize "retro-3D pixelation" shader over the 2.5D scene) and/or hundreds of sprites/particles at 60fps — the fidelity ceiling v2 `07` wanted without rigged glTF. **[C, mode-ii]** — needs a WebGPU-capable client (the streamer's box qualifies; phone viewers fall back to the A path). Must stay cosmetic/determinism-safe; honest tradeoff: bundle growth + capability-gated rendering (two render tiers to maintain).
- **(iii) Live GPU producer → Supabase.** **[C, mode-i-live]** — *rejected for this theme*, consistent with v2: a residential live-GPU producer is redundant against seed/clock broadcast (A#9/B), risks Supabase egress quota, and adds an uptime/security surface for a purely cosmetic gain. Keep the GPU offline.

*Why C is genuinely needed for its items:* neither offline high-fidelity baking (needs the GPU to *produce* the assets) nor live full-screen neural/shader post-FX at broadcast fidelity (needs WebGPU on the client) is reachable on B — B has no rendering horsepower beyond the CPU Canvas2D budget.

**One-line trap summary:** the substrate debate is over (v2 already built Canvas2D — v1's #1 is retired); the real unbuilt wins are **camera+replay** and **audio**, both Bucket A; the honest ceiling is **occlusion freezes audio too** (operational, not code); and the GPU's only defensible role is **offline asset factory (C-i)** or **client-side cosmetic post-FX (C-ii)** — never a live producer, never on the authority path.
