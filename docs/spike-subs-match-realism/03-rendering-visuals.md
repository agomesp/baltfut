## Rendering & Visual Believability for the /subtests Live Pitch

I read the actual spike. The sim (`src/lib/subs-draft/match-sim.ts`, 673 lines) is a **pure-TS engine** with a clean boundary — `step(dt, progress)`, `snapshot()`, `scoreFor(side)` — and zero DOM/React coupling. That single fact dictates most of what follows: the engine is *already* portable to a Web Worker, and the render layer can be swapped without touching it. The render layer (`src/components/subs-draft/pitch-view.tsx`) is where the problems live: it fires **~11 React `setState` calls every rAF frame** (`setHomePos`, `setAwayPos`, `setBall`, `setBallTrail`, `setStats`…), each spawning a full reconcile that re-renders ~23 absolutely-positioned `<div>` billboard tokens. That is the CPU/GC hotspot, the jank source, and — because it's rAF-bound — the thing that freezes in a background tab. Everything is `output:export` static on GitHub Pages, 11 runtime deps. Constraints respected throughout: **no SSR, no server needed for any of the ranked wins below.**

### The core insight

The current architecture couples three things that should be separate: **simulation** (physics, believable), **state** (React, slow when ticked at 60fps), and **paint** (DOM tokens, fine for 23 nodes but wrong tool as ambition grows). The single highest-leverage move is to **stop routing per-frame motion through React**. React should own discrete UI (scoreboard, ticker, flashes); a canvas/imperative layer should own the 60fps motion. This unlocks nearly every other upgrade.

### Ranked upgrades

**1. Move the rAF loop off React state → imperative render (Canvas2D). [S–M, client-only] — QUICK WIN, do first.**
Replace the 11 `setState`-per-frame with one `<canvas>` and a `draw(snapshot)` call inside the existing rAF. Keep React for the scoreboard/ticker/GOAL flash (event-driven `setState`, cheap). Canvas2D trivially draws 23 dots, shadows, ball, trail, and body-facing at 60fps with near-zero GC. **Why it boosts realism:** it *frees the frame budget* so you can afford easing, trails, and more agents without dropping frames — jank is the #1 immersion killer. **Libraries:** none — raw `CanvasRenderingContext2D`. Effort is small because the sim already emits a clean snapshot; you're rewriting only the paint half of `pitch-view.tsx`. This is the foundation for #2, #4, #7, #8.

**2. Motion polish on the dots: body facing, easing, anticipation, secondary motion. [S, client-only] — QUICK WIN.**
Dots read as alive when they *orient and lean*. Rotate each token toward its velocity vector (`atan2(vy,vx)`) — draw an ellipse (a facing body reads instantly better than a circle) with a small forward "nose." Add ease-out on target approach (the sim already has momentum/accel, so lean into it), a subtle bob, and squash on the ball at bounce. **Why:** motion caricature — anticipation + overshoot + follow-through — is exactly how Disney's 12 principles and every sports game (FIFA, eFootball) sell weight and intent. The ball trail already exists; make it velocity-scaled (longer trail = faster ball) and add a soft ground shadow that grows with ball "height" on shots/crosses to fake the 3rd dimension. Cheap, huge believability-per-hour.

**3. Camera work: pan/zoom-to-ball, cut on goal, slow-mo replay. [M, client-only] — the biggest *"we're watching a broadcast"* gain.**
A static top-down never feels televised. In Canvas2D this is a single `ctx.setTransform(scale, ..., -camX, -camY)` per frame, with `camX/camY` easing toward the ball (lerp, with a lookahead in the ball's velocity direction — how NBA 2K and FIFA's broadcast cam lead the play). On a `goal` event, **cut to a zoomed replay**: keep a 3–4s ring-buffer of snapshots (already tiny objects), then re-play them at 0.35× with the camera tight on the scorer and a "REPLAY" bug. This is the single feature that most makes it feel like a shared live event. **Trap to avoid:** don't chase the ball 1:1 (nausea) — use a dead-zone box and critically-damped easing.

**4. Fix the hidden-tab freeze: Web Worker sim + Page Visibility + setInterval fallback. [M, client-only] — CRITICAL, and your MEMORY.md already documents this pain.**
Port `createMatchSim` into a Worker (it's pure TS with no DOM — near-zero-effort move). The Worker steps on `setInterval(1000/30)`, which **keeps running in background tabs** (throttled to ~1s min, acceptable for a cosmetic sim), and posts snapshots to the main thread. Main thread renders via rAF *only when visible* (`document.visibilityState`); when hidden, skip painting but keep the clock. On refocus, you get correct state, not a frozen frame. **Important honesty from your own memory notes:** if the *window is fully occluded* (OBS/other-window-covering), Chrome freezes *pixels* regardless — no web fix. So this Worker approach fixes the common tab-switch case; the full-occlusion case stays a "keep the window visible / Modo Streamer PiP" operational workaround. Don't over-promise. `OffscreenCanvas` (transfer the canvas into the Worker and render there) is a nice extension but has Safari caveats — do the Worker-sim-only version first.

**5. Minimap/radar + broadcast overlays polish. [S, client-only] — QUICK WIN.**
A small corner radar (both teams as colored dots on a mini-pitch) is trivial once you have positions and massively raises the "tactical broadcast" feel — it's what every football broadcast and Football Manager's match engine shows. Also add lower-third name bugs on the ball carrier and on goals (you have scorer names already), and a possession-arrow/"LIVE" bug. All pure DOM/React overlay on top of the canvas; no per-frame cost.

**6. Player identity: pixel-art sprites via the existing PixelLab pipeline. [M, client-only] — the visual ceiling-raiser, but *sequence it after #1–#4*.**
The project already has a PixelLab AI pixel-art pipeline (per MEMORY.md, the craque-art experiment) and the PixelLab MCP is available. Generate an **8-direction run/idle sprite sheet** for a generic outfield player (recolorable per kit via a tint pass), plus keeper. Billboard the sprite in the canvas, pick the frame from the velocity angle, advance walk-cycle frame by speed. **Why:** identifiable little players beat abstract dots for emotional investment (subs are watching *their* squad). **Tradeoffs:** sprite sheets add a few hundred KB of PNG to the static bundle — fine for GitHub Pages if you ship *one* recolorable sheet, not 32 kits. **Trap:** do NOT go per-national-team art — bundle bloat + generation cost explodes. One sheet + CSS/canvas hue-shift.

**7. Upgrade to PixiJS (WebGL) only if you exceed Canvas2D's budget. [M, client-only] — conditional.**
Pixi is the right call *if* you add sprites (#6) with many animated players, particle celebrations, or want cheap filters (motion blur, glow). It batches sprites on the GPU where Canvas2D would start to sweat past ~50 animated sprites. **Cost:** ~150–450 KB gzipped added to a currently-lean bundle, and Pixi v8's WebGL/WebGPU init on a static host is fine but non-trivial. **Recommendation:** *don't reach for it yet.* Canvas2D handles 23 dots + trail + camera + replay comfortably. Adopt Pixi only when #6's sprite count or particle FX actually pushes Canvas2D past frame budget — measure first. Three.js is a **trap here**: true 3D is a huge asset/rigging/skeletal-animation investment (Spine/DragonBones/glTF) for a top-down football view where a faked 2.5D perspective (your current `rotateX` tilt, or a Canvas2D vertical-scale-by-depth) already reads as pseudo-3D at a fraction of the cost. Skip Three.js and skeletal animation.

**8. Ball physics height + shot/cross arcs in the render. [S, client-only] — QUICK WIN.**
The sim knows shots/crosses/corners. Give the ball a cheap parabolic `z` (height) purely in the render layer during those events: raise the sprite, grow+soften the ground shadow, add scale. Aerial believability for almost nothing — this is how 2D games fake the third dimension without a 3D engine.

### Summary ordering

Do **1 → 2 → 4 → 5 → 8** first: all Small-to-Medium, client-only, and together they convert the spike from "dots teleporting via React state" into a **jank-free, background-tolerant, camera-driven mini-broadcast** — the largest believability jump for the least effort and *zero* new hosting cost. Then **3 (camera/replay)** and **6 (PixelLab sprites)** for the "watching a real match together" ceiling. Hold **7 (Pixi)** until measured need, and **avoid Three.js/skeletal (2.5D fakery wins on this budget)** and **avoid per-team art (bundle trap)**. Nothing here needs Supabase or a paid server — realism lives entirely on the client; the cheap-server budget is better spent (if ever) on a **server-authoritative Worker-equivalent sim shared over Supabase Realtime broadcast** so every viewer sees the *same* frame — but that's a separate "watched together in sync" study, not a rendering one.
