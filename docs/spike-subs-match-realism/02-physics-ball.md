# Ball & Player Physics for the /subtests Match Sim

## What exists today (grounding)

The engine (`src/lib/subs-draft/match-sim.ts`, ~673 lines) is a **2D, no-height** semi-implicit Euler integrator stepped by `requestAnimationFrame` in `pitch-view.tsx` with a variable `dt` clamped to 0.05s. The ball is `{x,y,vx,vy}` on a 100×100 plane; friction is exponential decay (`v *= Math.exp(-friction*dt)`) with two constants (`BALL_FRICTION=1.35` rolling, `SHOT_FRICTION=0.3` struck). Players seek a target via desired-velocity minus current-velocity, capped at `ACCEL*dt` — a decent momentum model, but heading changes are instantaneous (no turning radius), top speed is a flat `JOG/SPRINT * pace * stamina`, and there's no reaction lag beyond a coarse `rt` re-target timer. "Collisions" are a soft circle-push `separate()` that doesn't conserve momentum. Everything branches on `Math.random()`, so nothing is replayable. The scoreline is authoritative; the sim only has to *look* believable.

That last fact is the strategic key: **you don't need a real physics library.** Box2D-family solvers exist to *discover* emergent outcomes (stacking, jointed ragdolls) you don't control. Here the outcome is scripted — so a heavy WASM solver buys you determinism headaches and bundle weight while solving a problem you don't have. The believability gap is almost entirely in **ball trajectory (height + spin)** and **player kinematics (turning + reaction)**, both cheap to add to the bespoke integrator.

## The library question (settled first)

- **matter.js** (~90KB): easy, but it's an iterative sequential-impulse solver — *non-deterministic* across machines and famously order-sensitive. Wrong tool: you'd fight it to script goals.
- **planck.js / Box2D-WASM / rapier2d**: rapier is deterministic *by design* (fixed-point-ish, cross-platform), which is genuinely attractive if you later run the sim server-side for shared viewing. But all three are 2D-plane solvers with **no z-axis** — a football's defining trait (loft, headers, keeper claims, the dipping shot) is a *height* dimension they don't model any better than your own code. You'd bolt a manual `z` on top of them anyway.
- **Verdict: keep the bespoke integrator.** It's already frame-rate-independent and you control every outcome. Invest the same effort into a richer ball model and player kinematics instead. Reach for a lib only if you adopt an authoritative **server-side sim** (see #7), where rapier2d's determinism earns its keep.

## Ranked upgrades

### 1. Add a ball height axis (z, vz, gravity) — *the single biggest jump*. Effort: M. Client-only.
Right now crosses, corners, headers, goal kicks and long balls are **flat drags across the grass** — the giveaway that this isn't real football. Add `z`, `vz`, gravity (`vz -= g*dt`, `z += vz*dt`, bounce with restitution ~0.6 and a horizontal-friction bleed on ground contact). Passes stay z≈0; crosses/goal-kicks/corners/lofted through-balls get launch `vz`; headers only connect when `z` is in a 1.7–2.4 "head zone"; keepers claim high balls. Render `z` as token lift + a scaling ball sprite + a grounded shadow you already draw. This is *the* believability multiplier — it makes aerial play, headers, and the keeper's world suddenly legible. Reference: this is exactly the projectile+bounce model FIFA/PES and the open-source **GameplayFootball / Gameplay Football (BeGround)** engine use; a full rigid-body solver is overkill for a point-mass ball. **Quick win within this: shadows already exist**, so the visual scaffolding is half-built.

### 2. Magnus spin/curve on struck balls. Effort: S–M. Client-only.
Add a scalar `spin` set at kick time and apply a lateral acceleration perpendicular to velocity each step: `a_perp = k_magnus * spin * speed`, rotating `(vx,vy)`. Free kicks, corners (in-swing/out-swing), crosses and finesse shots then **bend** — the difference between "a dot slid to the corner" and "he *curled* it." Combine with #1 and you get the dipping/swerving shot. Cheap, pure math, huge perceptual payoff. Reference: the standard Magnus term `F = k(ω×v)`; arcade footballers approximate it exactly this way with a single curve coefficient. Tune `k` by eye — believability, not aerodynamics, is the goal.

### 3. Player turning radius + reaction lag. Effort: S. Client-only.
Two small changes to `steer()`: (a) cap the **angular** change of the velocity vector per step (e.g. max ~6–9 rad/s scaled by inverse speed), so fast players can't reverse instantly — they arc, overrun, and have to decelerate to cut back; (b) add a per-player `reactionDelay` (80–250ms by rating) before a new target is pursued. Today the flat `ACCEL` cap gives linear momentum but pivots are free, which reads as "hockey air-bots." Turning radius + lag is the cheapest thing that makes bodies feel like they have *mass and eyes*. Reference: steering-behaviours literature (Reynolds) — you already do "seek/arrive"; add "turn-rate clamp," the standard next step.

### 4. Attribute-driven kinematics (accel, decel, top speed, agility). Effort: S. Client-only.
`pace` is currently one derived number. Split into `topSpeed`, `acceleration`, and `agility` (turn rate) per player so a rangy target-man and a twitchy winger *move differently*. Decel-into-target already exists (the `d<5` ramp); make braking distance scale with speed so sprinters overrun. Near-free once #3's machinery is in, and it makes the draft's rating choices *visible* on the pitch — which is the whole point of a fantasy draft game.

### 5. Momentum-conserving jostling / shielding. Effort: M. Client-only.
Replace the symmetric `separate()` push with a mass-weighted, velocity-aware contact: heavier/stronger players win the collision, the carrier can **shield** by putting body between ball and challenger, and shoulder-to-shoulder contests nudge the loser off-line. This makes 50/50s and hold-up play believable instead of two dots politely repelling. This is the one place a real solver *would* help (contact manifolds), but a hand-rolled "resolve overlap along the normal, split by mass, damp tangential" is ~30 lines and stays deterministic. Trade-off: tuning to avoid jitter.

### 6. Fixed-timestep accumulator + seeded RNG (determinism). Effort: S. Client-only (enables server later).
Currently `dt` varies with frame rate and the sim reads `Math.random()`, so the same match looks different every run and **can't be replayed or shared**. Wrap the step in a fixed-timestep accumulator (step at a constant 1/60s, render-interpolate the remainder) and replace `Math.random()` with a **seeded PRNG (mulberry32/xoshiro, ~5 lines)**. Now a `(matchId, seed)` pair fully determines the match. This is a **quick win and a keystone**: it fixes numerical consistency, makes the sim testable (you already have `match-sim.test.ts`), and unlocks #7 — every viewer replays the identical match from a seed broadcast over Supabase. **Trap avoided:** without this, any "watch together" feature drifts per client.

### 7. Ball-flight polish: rolling vs sliding friction, deflection ricochets, keeper parries with spin. Effort: M. Client-only.
Once #1–#2 land: (a) distinguish a struck ball that *slides* then transitions to *rolling* (higher friction) — the decelerating-then-settling ball reads as real; (b) deflections/blocks (you have `BLOCK_R`) should reflect off the body normal with restitution and carry a fraction of spin, not the current random scatter; (c) parries push the ball out at a believable angle. Incremental, but it's the texture that sells loose-ball scrambles and rebounds.

### 8. (Only if you go server-authoritative) rapier2d-WASM for a shared, deterministic sim. Effort: L. Needs cheap server / Supabase Edge (Deno).
If "watched together" becomes core, run the sim once on a **Supabase Edge Function (Deno, WASM-capable)** or a cheap server and broadcast state/seed via Supabase Realtime. Here rapier2d's cross-platform determinism is worth its weight — but you'd *still* hand-roll ball height on top. Only pursue if #6's seed-broadcast approach (far cheaper, static-friendly) proves insufficient. **Trap:** don't adopt rapier *client-side* for its own sake — WASM load, no z-axis, and a solver you must fight to script goals.

## Quick wins vs traps

**Quick wins:** #6 seeded-PRNG + fixed timestep (hours, unlocks replay/sync), #2 Magnus curve (hours, dramatic shot/FK payoff), #3 turning radius (hours, bodies gain mass). **Biggest single jump:** #1 ball height. **Traps:** adopting matter.js (non-deterministic) or any 2D solver client-side expecting football physics for free — none model height, and the scripted-scoreline design means an emergent solver actively fights you. Given the rAF-freezes-when-hidden limitation, #6's determinism also means a backgrounded tab can **fast-forward from the seed** on refocus instead of freezing mid-play — a bonus fix.
